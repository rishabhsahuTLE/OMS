## Commands

- `npm run dev` — start the Vite dev server (HMR).
- `npm run build` — type-check via `tsc -b` then `vite build`.
- `npm run lint` — run oxlint (`.oxlintrc.json`; plugins: react, typescript, oxc).
- `npm run preview` — preview the production build.

There is no test runner configured in this project.

## Architecture

OMS (Order Management System) is a single-page React 19 + TypeScript app with **no router and no backend** — all state lives in `App.tsx` via `useState` and is seeded from static mock data. There is no persistence; a page refresh resets everything to the mock data.

**Navigation** is a hand-rolled tab system, not a router:
- `App.tsx` owns `activeTab` (`MainTabId`), plus per-section sub-tabs (`activeReportSubTab`, `activeOrdersSubTab`), and switches pages with if/else in `renderPage()`.
- `Sidebar.tsx` renders the nav and calls `onSelect(tab, subTab)` — it does not own routing state itself, only its own expand/collapse UI state.
- Page title in the header bar is derived from a `TITLES` lookup keyed by `"section/subsection"` strings — update this map when adding a new tab/sub-tab.

**Sections**: Dashboard (placeholder) · Report (Approval, Billing[placeholder]) · Order Management (Account, Order, Closing Bill[placeholder]). `PlaceholderPage` is the stub used for anything not yet built.

**Domain model** (`src/types.ts`) — the two core entities:
- `Account`: a customer org, with billing/delivery address and a list of `Spoc` (point of contact).
- `OrderRecord`: an order against an account for a `service` (`SERVICES`: `"Saas(LMS)"` | `"Quirio"`). Each order has two independent approval stages, `technical` and `financial` (`StageStatus` = status + date-when-decided), used throughout Approval/Order List to compute "days taken" and closed/open state (`isFullyConfirmed` / `isClosed` — both require *both* stages `confirmed`, duplicated in `OrderPage.tsx` and `Approval.tsx` rather than shared).
- `OrderRecordDetails` holds the full order form payload, including a per-service field split: `numUsers`/`feePerUser` for Saas(LMS) vs. `unitPrice`/`assessments`/proctoring flags/etc. for Quirio. `CreateOrderModal.tsx` branches its form and net-amount calculation (`isSaas`) on which service was selected.
- Order numbers are generated by `nextOrderNumber` (`utils.ts`): first order for an account gets the next sequential `OD-P0000147`-style base; repeat orders for the same account get a letter suffix (`OD-P0000147A`, `...B`, ...).

**State flow**: `App.tsx` holds `accounts`/`orders` arrays and passes them + mutator callbacks (`onCreateAccount`, `onCreateOrder`, `onDeleteOrder`) down as props — no context, no external state library. Creating an order from the Order tab when the target account doesn't exist yet routes through `handleNavigateToAddAccount`, which switches to the Account sub-tab and sets `autoOpenAccountModal` to auto-open `CreateAccountModal` (consumed once via `autoOpenModal`/`onAutoOpenHandled` in `Account.tsx`).

**List/filter pattern** (repeated in `Account.tsx`, `OrderPage.tsx`, `Approval.tsx`): each list page keeps *draft* filter state (per-field) separate from *applied* filter state, only committing draft → applied on an explicit Search click; filtering itself is a `useMemo` over the applied state. Approval additionally supports column sorting via a `{ key, direction }` sort state and a `compareByKey` switch.

**Mock data** (`src/data/mockAccounts.ts`, `mockOrders.ts`) is deterministic, generated from a **fixed reference date** (`2026-07-21` in `mockOrders.ts`) rather than `Date.now()`, so seed data doesn't shift day to day. `CURRENT_USER_EMAIL` (`utils.ts`) is the hardcoded stand-in for the logged-in user, since there's no auth.

**Dates** are stored as ISO strings (`yyyy-mm-dd`) everywhere in state/mock data, converted to `Date` only for computation, and formatted for display with either `formatDDMMYYYY` (`utils.ts`) or `toLocaleDateString("en-IN", ...)` (used in `Approval.tsx`) — parsing goes through `parseISO`-style manual `split("-")` rather than `new Date(isoString)` to avoid UTC/local timezone shifts.

**Styling** is Tailwind v4 utility classes only (no component library) — colors follow a convention: slate for neutral chrome, indigo for primary/selected nav and dashboard accents, teal for action buttons (Search/Add/Create), emerald/rose/slate for confirmed/rejected/pending status. Icons are inline hand-drawn SVGs (no icon package dependency).

`Modal.tsx` is the shared dialog shell (backdrop click + Escape to close); both `CreateAccountModal` and `CreateOrderModal` build their forms inside it. `DateRangePicker.tsx` is a shared custom calendar-range picker (no date library dependency) used by both Order List and Approval filters.
