# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server (HMR).
- `npm run build` — type-check via `tsc -b` then `vite build`.
- `npm run lint` — run oxlint (`.oxlintrc.json`; plugins: react, typescript, oxc).
- `npm run preview` — preview the production build.

There is no test runner configured in this project.

## Session start

At the start of a session in this repo, proactively run the `repo-housekeeper` subagent once (before other work) to verify `.gitignore`, `README.md`, `CLAUDE.md`, and the Vercel-hosting config are current. Skip it only if it was already run earlier in this same session.

## Deployment

This must always stay a **plain static Vite build with zero backend dependencies**, so it can be pushed to GitHub as-is and deployed on Vercel with no extra setup: no server-only APIs, no required environment variables, no build step beyond `npm run build` (`tsc -b && vite build`) producing static assets in `dist/`. `vercel.json` pins the framework preset explicitly. Don't introduce anything (a Node server, an env-gated feature, a non-static asset pipeline) that would break a zero-config Vercel deploy without calling it out.

## Architecture

OMS (Order Management System) is a single-page React 19 + TypeScript app with **no router and no backend** — all state lives in `App.tsx` via `useState` and is seeded from static mock data. There is no persistence; a page refresh resets everything to the mock data.

**Navigation** is a hand-rolled tab system, not a router:
- `App.tsx` owns `activeTab` (`MainTabId`), plus per-section sub-tabs (`activeReportSubTab`, `activeOrdersSubTab`), and switches pages with if/else in `renderPage()`.
- `Sidebar.tsx` renders the nav and calls `onSelect(tab, subTab)` — it does not own routing state itself, only its own hover-driven UI state (see below).
- Page title in the header bar is derived from a `TITLES` lookup keyed by `"section/subsection"` strings — update this map when adding a new tab/sub-tab.

**Sidebar** is hover-driven, not click-driven, and rests collapsed to an icon-only rail (`w-16`): hovering anywhere on the `<aside>` expands it to `w-64` (labels visible), and moving the cursor off it collapses everything back — `collapseAll()` resets both the rail and any open category dropdown. Hovering the "Report", "Order Management", or "Admin" row independently drops down its sub-tab list (`reportHovered`/`ordersHovered`/`adminHovered` state) and collapses when the cursor leaves *that* row; clicking a category navigates to its current sub-tab rather than toggling anything. Nothing here is click-to-toggle anymore — if you add a new category, wire it the same hover way, not with a click handler that flips a boolean.

**Sections**: Dashboard (placeholder) · Report (Approval, Billing, Manager Report) · Order Management (Manage Orders, Amend / Cancel, Close Billing) · Admin (Approval Setting). `PlaceholderPage` is the stub used for anything not yet built. There is no client-management (CRUD) page — `Client` records are static, seeded entirely from `src/data/clients.json`; order creation only lets you pick an existing client. Order Management's sub-tab order in `Sidebar.tsx`'s `ordersSubTabs` is deliberately Manage Orders first (it's the day-to-day landing point — both order creation and activation/cancellation approval live there), then Amend/Cancel, then Close Billing — this is display order, not lifecycle order; don't reorder it back to lifecycle order without checking with the user first. There is no standalone "Create" sub-tab — creation lives behind a **Create** button inside Manage Orders (see below); `OrdersSubTabId`'s `"approval"` value/id is unchanged from when the tab was literally called Approval, only its sidebar `label` became "Manage Orders" (`Sidebar.tsx`'s `ordersSubTabs`) and its `TITLES` entry became "Order Management / Manage Orders" — don't rename the id itself, it'd be a no-op churn touching every prop/branch keyed on it.

**Amend / Cancel** (`OrderPage.tsx`, id `"amendCancel"` — the filename predates the rename) lists orders with `lifecycleStatus === "active"` — no create button (creation is Create's job now), no T/F columns (everything shown is already fully activated). Each row has two actions instead of Edit/Delete: **Amendment** opens `CreateOrderModal` in edit mode, fully prefilled from the order being amended, but — unlike editing a not-yet-active order — only a fixed field set stays editable (see **Create**'s amendment-restriction note below); **Cancellation Initiation** opens `CancellationConfirm.tsx`, which now collects mandatory cancellation details before it'll let you proceed (see **Order lifecycle** below), independent of any amendment. Clicking Update on an amendment does **not** commit right away — `handleModalUpdate()` (passed as `CreateOrderModal`'s `onUpdate`) stashes the pending change and opens a `ConfirmDialog` ("Confirm Amendment") spelling out the consequence: `{base}/{n}` will be created Inactive needing fresh Tech/Fin approval, and `{base}` will immediately have cancellation initiated needing TC/FC approval, with `{base}/{n}` only going Active once both finish and `{base}`'s billing is closed. Only on confirming (`confirmAmendment()`) does it actually commit two mutations at once: a brand-new **successor** record under a versioned order number (`${base}/${n}` — e.g. `OD-P0000141/1`, then `/2` on a further amendment of that successor — via `baseOrderNo()`/`utils.ts`) carrying the edited details, `lifecycleStatus: "inactive"`, all four stages reset to pending, `amended: true`, and `supersedes` set to the predecessor's `id`; and the predecessor itself flipped straight to `lifecycleStatus: "cancellationInProgress"` (no separate button click needed — this *is* the cancellation initiation). Cancelling the dialog just discards the pending change and leaves the edit form open. From here the two orders run **independent, parallel approval chains** — the successor through Tech/Fin (see **Order lifecycle** below), the predecessor through TC/FC — and only converge back together at Close Billing (see below). This versioning only applies when the pre-edit record was `active`; edits reached some other way (e.g. the duplicate-order handoff below, before an order has ever activated) just update in place, no successor spawned, no confirmation needed.

**Manager Report** (`src/pages/ManagerReport.tsx`, a `ReportSubTabId` alongside Approval/Billing — not a top-level tab) groups `orders` by `clientManager` into one summary row per manager (Total/Technical/Financial/Confirmed/Rejected/Amount, via `buildManagerStats()`). Each row expands independently — `openManagers` is a `Set<string>` of manager names, so any number of rows can be open at once, not an accordion — revealing a per-manager `ManagerOrdersTable` (its own local search + Show-N-entries + pagination) in the row directly below. The expand affordance is `ExpandIcon`, the same rotate-90-on-open chevron motif as `Sidebar.tsx`'s section arrows.

**Domain model** (`src/types.ts`) — the two core entities:
- `Client`: a customer org, with billing/delivery address and a list of `Spoc` (point of contact).
- `OrderRecord`: an order against a client for a `product`. Product identity and per-product form behavior are centralized in `src/products.ts` — each product is a `Product` subclass (currently `LmsProduct` → name `"LMS"`, and `QuirioProduct` → name `"Quirio"`) listed in the `PRODUCTS` array; `PRODUCT_NAMES` is derived from it and is the only place product names are read from, so renaming/adding a product only touches `products.ts`. `Product.fields(values)` is a **method**, not a static list — it exists so Quirio can reorder/re-require its `numUsers`/`assessments`/`unitPrice` fields based on the current `billedOn` value (whichever of "No. of Users"/"No. of Assessments" is selected becomes mandatory and moves first; LMS just ignores `values` and returns a fixed list) — every call site passes the live form values, not a cached list. Each order has two independent activation-approval stages, `technical` and `financial` (`StageStatus` = status + date-when-decided + optional `processedBy`/`remark`), plus two cancellation-approval stages `cancellationTechnical`/`cancellationFinancial` — see **Order lifecycle** below for how those four combine with `lifecycleStatus`. `Approval.tsx` still separately computes a simple "both activation stages confirmed" boolean for its own purposes (`isFullyCleared`) — that's unrelated to the lifecycle used by Order Management's Manage Orders tab. `orderNo` is usually its own thing, but can carry a `"/N"` version suffix once it's an amendment successor (see **Amend / Cancel** above) — `amended: true` marks that (permanently, even once it's gone `active`), and is what every table's yellow-row highlight keys off. `supersedes` (only set on a successor) is the id of the predecessor order it was amended from — the authoritative link for predecessor/successor lookups, since `orderNo` string-parsing alone can't disambiguate multiple amendment generations of the same order.
- `OrderRecordDetails` holds the full order form payload, including a per-product field split (e.g. `numUsers`/`feePerUser` for LMS vs. `unitPrice`/`assessments`/proctoring flags/etc. for Quirio, declared in each `Product.fields`), plus shared billing-schedule fields: `firstBillingMonth` (`yyyy-mm`, the FBD used in Billing revenue projection), `billingCycle` (`BillingCycle`), and `agreement` (contract length in months) — together these determine which months an order bills in.
- Order numbers are generated by `nextOrderNumber` (`utils.ts`): first order for a client gets the next sequential `OD-P0000147`-style base; repeat orders for the same client get a letter suffix (`OD-P0000147A`, `...B`, ...).

**State flow**: `App.tsx` holds `orders` (and `clients`, read-only from the JSON seed) and passes them + mutator callbacks (`onCreateOrder`, `onUpdateOrder`, billing-status setters) down as props — no context, no external state library. There's no delete-order path anymore (removed along with `OrderPage.tsx`'s old Edit/Delete list — amending/cancelling are the only mutations now). Client and product selection for order creation live *inside* `CreateOrderModal.tsx` (not the page rendering it) — see **Create** below.

**List/filter pattern** (repeated in `OrderPage.tsx`, `CloseBilling.tsx`, `ManagerReport.tsx`): most list pages keep *draft* filter state (per-field) separate from *applied* filter state, only committing draft → applied on an explicit Search click. `Approval.tsx` and `Billing.tsx` instead apply filters live via `useMemo` with no explicit Search step. Approval additionally supports column sorting via a `{ key, direction }` sort state and a `compareByKey` switch. Every list/report table's `<thead>` is sticky (`sticky top-0` per `<th>`, each with its own opaque `bg-*` so scrolled body rows don't show through) — keep new tables consistent with this.

**Billing** (`src/pages/report/Billing.tsx`) is a revenue-projection table over `orders`. Filtering is a live text `search` box (client/order#/manager) plus a small funnel-icon button that opens `FilterDrawer.tsx` — a generic right-anchored drawer (dark header, left category rail, right detail pane, Clear/Apply footer) reused here for Client/Product/Client Manager/Amount/Order Status/Created On; unlike the live search, the drawer's filters use draft-vs-applied state (`draft`/`applied`, committed only on Apply) since each category is edited one at a time behind an explicit confirm step. The "Created On" category renders `InlineDateRangeCalendar.tsx` — a two-month-side-by-side calendar (single prev/next pair on the outer edges) rather than `DateRangePicker.tsx`'s single-month popover, matching the drawer's always-visible layout. The table's fixed 12 month columns are a rolling **April–March fiscal year** computed from the real current date (`buildFiscalYearColumns`), not the mock reference date; a given order bills its `amount` in a column when `billsInColumn()` finds that column falls on a cycle occurrence starting from `details.firstBillingMonth`, stepping by `CYCLE_STEP[billingCycle]` months, bounded by `details.agreement` months if set. The first table row is always the column-wise total across the currently filtered orders, and — like the header — is sticky (pinned just below it, at `top-11`). The column for the current real-world month is highlighted amber end-to-end (header/total/every body row), via each `FyColumn.isCurrent` flag. The Client/Order #/Product columns are also frozen horizontally (`sticky left-0/[180px]/[310px]`, fixed pixel widths kept in sync between header/total/body via the `CLIENT_COL`/`ORDERNO_COL`/`PRODUCT_COL` class constants) so they stay visible when scrolling right through the month columns; body rows use `group`/`group-hover` so the frozen cells still pick up the row-hover tint despite needing their own opaque background. `statusBucketOf()` sorts each order into exactly one of `technical` / `financial` / `neither` for the Order Status filter — because financial clearance can't happen before technical, this partition is naturally mutually exclusive. The "Amount (₹)" header carries an `InfoTooltip` (hover shows it via CSS `group-hover`, click toggles an independent boolean — kept separate so a real click's own hover-in doesn't immediately re-close what hovering opened).

**Approval** (`src/pages/report/Approval.tsx`) only ever lists orders where both `technical` and `financial` are `"confirmed"` (`isFullyCleared()`) — there's no status filter, since every row is definitionally "closed". Columns (matching a legacy report layout) label `client`/`clientManager` as "Account"/"A/C Manager" for display only, the domain fields are unchanged. No confirmed/rejected icons — since every row already cleared both stages, `DaysCell` just shows the plain day count (unit is stated once in the "Time Taken (in days)" group header, not repeated per cell). Its Amount filter reuses `AmountRangeSlider`, same as Billing and Manager Report.

**Create** (`src/pages/orders/CreateOrderModal.tsx`) owns client/product selection itself — two selects at the top — and gates the rest of the form (client details, contact details, order/billing details) behind both being chosen and there being no blocking duplicate (`ready = client !== null && currentProduct !== null && duplicateOrder === null` — the duplicate-order guard, below, must resolve before the rest of the form is even shown, not just before it's submittable). Passing `embedded` renders the same form directly on a page (no `Modal`/backdrop, no `max-h-[85vh]` scroll cap) instead of inside `Modal.tsx`; embedded instances have no "close" to return to, so Cancel becomes **Reset**, calling `onReset` instead of `onClose` — `App.tsx` implements `onReset` by bumping a `createOrderKey` counter used as the component's `key`, which remounts it with fresh state (this is also how it resets itself after a successful save). There is no dedicated "Create" tab — `OrderApproval.tsx` (Manage Orders) renders `CreateOrderModal` with `embedded` set behind a local `creating` boolean, toggled by a **Create** button in its own top bar (view-filter tabs on the left, Create on the right) and a "Back to Manage Orders" link in place of a page title while open; `OrderPage.tsx` (Amend / Cancel) still renders it as a modal for its own Amendment flow. Inside the form, changing the product resets that product's fields (prefilled from `editingOrder` only if it's the same product), and changing the client (on a new, non-editing order) resets the SPOC list so a previous client's contacts don't linger. **Duplicate-order guard**: whenever the picked client is `type === "University"` and already has an order for the picked product, a `ConfirmDialog` asks whether to amend the existing one instead — "Yes" calls `onRequestAmend(existingOrder)`, which `App.tsx` wires (for the embedded Create view inside Manage Orders) to jump to Amend / Cancel and auto-open that order for editing via `editOrderId`/`autoOpen` on `OrderPage`, and which `OrderPage.tsx` wires (for its own modal) to just swap the currently-open modal into edit mode for it. Dismissing the dialog without choosing "Yes" does **not** clear `duplicateOrder`, so the rest of the form stays hidden until the client or product selection changes to a non-duplicate combination.

**Amendment field restriction**: `isAmendingActiveOrder` (`CreateOrderModal.tsx`) is true only when `editingOrder.lifecycleStatus === "active"` — a genuine amendment via Amend/Cancel, as opposed to editing an order that hasn't activated yet (e.g. completing an incomplete/duplicate-handoff order), which stays fully editable exactly like Create. When true, only **Product**, **No. of Users**, **Rate** (`feePerUser`/`unitPrice` — whichever the product has, via the `AMENDMENT_EDITABLE_PRODUCT_FIELDS` set), **Payment Terms** (the `Plan` field), **First Billing Month**, **Agreement**, and **Advance** stay editable; everything else (Date of Sign, One Time, GST Process, Billing Cycle, TDS, Credit Period, Remarks, all SPOC/Contact editing, all Document editing, and every other per-product field like Quirio's `billedOn`/proctoring flags/question type/device type) is disabled — shown for reference, not editable — with a banner above Client Details spelling out the allowed set. One escape hatch: if the amender actually changes the product (`productChanged`), that product's whole field section unlocks instead of locking to a permanently-blank, unsavable state — there's no prior value to preserve for a product that wasn't there before.

**Order lifecycle** (`OrderLifecycleStatus` in `types.ts`) drives Order Management's **Manage Orders** tab (`src/pages/orders/OrderApproval.tsx` — the filename/id predate the rename from "Approval"): `inactive` (new order, awaiting **Tech**/**Fin** activation approval) → `active` (both confirmed) →, once cancellation is requested (from Amend / Cancel's "Cancellation Initiation", the review page's button, or automatically as part of confirming an amendment — see **Amend / Cancel** above), `cancellationInProgress` (awaiting **TC**/**FC** cancellation approval) → `cancelled`. An amendment **successor** takes a detour at the top of this chain instead of going straight `inactive` → `active`: once its Tech+Fin are both confirmed it lands on `pendingClosure` (`withRecomputedLifecycle()`, keyed off the record having `supersedes` set) and sits there — still shown as "Pending Closure" in Manage Orders, its own `ViewTab`/badge entry — until the predecessor it superseded finishes TC/FC *and* has its billing closed; only then does it become `active` (see **Close Billing** below for exactly where that flip happens). The list itself is **display-only** — `StageBadge` just renders each stage's P/✓/✕, no click-to-change — because approvals are enforced strictly in order (Tech must be confirmed before Fin is actionable, TC before FC) and can only happen through the review/process page. Every row's Status cell also carries an **i (info) button** — `nextStepInfo()` in `OrderApproval.tsx` — opening a small popover naming the concrete next action for that order's current `lifecycleStatus`: which stage (Tech/Fin/TC/FC) is next via `getNextActionableStage()` for `inactive`/`cancellationInProgress`; for `pendingClosure`, it looks up the predecessor via `supersedes` and either names the TC/FC stage it still needs (with a "Review `{predecessor}`" button that jumps straight to that predecessor's own review page via `setReviewOrderId`) or tells you to close its billing (with a "Go to Close Billing" button, wired through the `onNavigateToCloseBilling` prop from `App.tsx` since that's a different sub-tab); for `cancelled` orders needing Close Billing it's the same "Go to Close Billing" action. The one case with **no action button at all** is a `cancelled` order whose `billingStatus` is already `"Closed"` — that popover collapses to just "Billing has been closed for this order." plus the dismiss (Close) button, since there's genuinely nothing left to do or navigate to. Clicking a row's Edit icon (the **Action** column) opens `OrderApprovalReview.tsx` in place of the list (a local `reviewOrderId` swap inside `OrderApproval.tsx`, no App-level routing involved), which shows: `OrderDetailsReadOnly.tsx` (Account/Contact/Order/Payment/Document sections, all disabled — shared with `CancellationConfirm.tsx`, see below); a **Changes From `{predecessor orderNo}`** table — only rendered when the reviewed order is an amendment successor (has `supersedes` set) — built by `diffOrderDetails()` (`utils.ts`) diffing the successor against the predecessor looked up by id (`orders.find(o => o.id === order.supersedes)` — not `orderNo` string-parsing, which would break across multiple amendment generations), listing every field (shared order/billing fields plus whichever per-product fields apply) whose value actually changed, old value struck through in rose, new value in emerald; an **Approval History** table listing all four stages (Tech/Fin/TC/FC) with status ("Pending"/"Accepted"/"Rejected"), processed-by, processed-on, and remark; and a **Process Order** form that's the only editable part. `getNextActionableStage()` (`utils.ts`) finds the first not-yet-confirmed stage in the order's current sequence (Tech→Fin, or TC→FC once cancellation is in progress) and that's the sole "Approval Type" the form allows acting on — there's no way to pick a different stage out of order. Submitting requires the re-entered "Agreement Amount" to exactly match `order.amount` (a fat-finger guard) before it writes the new status/date/`processedBy`/remark onto that stage and calls `withRecomputedLifecycle()` (`utils.ts`) to promote `inactive`→`active` (or `inactive`→`pendingClosure` for a successor) or `cancellationInProgress`→`cancelled` if both of that pair's stages are now confirmed. When `lifecycleStatus === "active"`, the Process Order section is replaced by a single "Request Cancellation" button — clicking it doesn't fire immediately; it flips a local `requestingCancellation` flag that swaps the whole page for `CancellationConfirm.tsx` (the same component and mandatory fields Amend/Cancel's "Initiate Cancellation" uses — see below), and only actually calls `onRequestCancellation` once that form is confirmed; when `"pendingClosure"`, it's replaced by a note naming the predecessor order and saying it's waiting on that order's TC/FC + billing closure; when `"cancelled"`, it just says there's nothing left to do.

**Cancellation initiation** (`CancellationConfirm.tsx`) is the single point both entry points above route through — it can't be confirmed without **Effect From Date**, **Outstanding Balance (₹)**, and **Reason for Cancellation** (validated on submit, same pattern as `CreateOrderModal`'s own validation); **Comments** is the one optional field. These four fields make up `CancellationDetails` (`types.ts`), stored on the order as `cancellationDetails` once confirmed — permanent from that point on, alongside the `lifecycleStatus: "cancellationInProgress"` flip (`OrderPage.tsx`'s `cancelTarget` flow sets both together, as does `OrderApprovalReview.tsx`'s `requestingCancellation` flow via `onRequestCancellation(order, details)`). `OrderDetailsReadOnly.tsx` renders a **Cancellation Details** section once `order.cancellationDetails` is set, so it shows up automatically on the TC/FC review page for approvers — absent before initiation (nothing to show yet), so it never appears on `CancellationConfirm.tsx` itself.

**Close Billing** (`CloseBilling.tsx`) is where a predecessor/successor pair from an amendment finally reconverges. `isClosable(order, allOrders)` requires `lifecycleStatus === "cancelled"` as before, but if some other order's `supersedes` points back at this one (i.e. it was superseded by an amendment), it additionally requires that successor to have already reached `pendingClosure` (or, defensively, `active`) — so the row simply doesn't appear here until *all four* stages (the successor's Tech+Fin and the predecessor's TC+FC) are done, exactly matching the guarantee described in the Amend / Cancel confirmation dialog. Orders cancelled the ordinary way (no amendment involved, no order's `supersedes` pointing at them) are unaffected and closable as soon as they're `cancelled`, same as always. Actually performing the close — `App.tsx`'s `handleSetBillingStatus` when called with `"Closed"` — is the one and only place a successor is promoted from `pendingClosure` to `active`: for every order just marked Closed, it looks up the order (if any) whose `supersedes` equals that order's `id` and, if it's sitting at `pendingClosure`, flips it to `active` in the same state update. Marking a batch "Closed" surfaces a plain summary `Modal` (`closedBatch` state) listing every order number just closed, plus one shared `closedRemark` textarea ("Remarks (applies to all orders above)"), and an "Okay" button — it does **not** prompt to create a follow-up order (no "Create Order Now"/"Create Order Later" choice); that prefill-and-redirect flow was removed along with `App.tsx`'s `handleCreateOrderNow`/`handleCreateOrderLater`. Dismissing the popup (Okay, backdrop click, or Escape all route through `dismissClosedBatch`) applies that one remark — if non-empty — to every order in the batch via `onUpdateBillingRemarks`, overwriting each one's existing `billingRemarks`; leaving it blank leaves each order's remark untouched.

**Row highlighting is a house convention, not a one-off**: every table that lists `OrderRecord`s (`OrderApproval.tsx`, `Approval.tsx`, `Billing.tsx`, `ManagerReport.tsx`'s per-manager sub-table, `CloseBilling.tsx`) highlights the whole row yellow when `amended` and red when `lifecycleStatus === "cancelled"` (each file has its own small `rowHighlight`/`rowHighlightClass` — not shared, since Billing's frozen sticky-left columns need a second matching class for their own background). `CloseBilling.tsx` only does yellow, since every row there is already cancelled by definition — a uniform red would say nothing. Add the same pair of classes to any new order table rather than inventing different colors.

**Mock data** (`src/data/clients.json`, `mockOrders.ts`) is deterministic, generated from a **fixed reference date** (`2026-07-21` in `mockOrders.ts`) rather than `Date.now()`, so seed data doesn't shift day to day. `CURRENT_USER_EMAIL` (`utils.ts`) is the hardcoded stand-in for the logged-in user, since there's no auth. Every seeded order's `details` must be filled in as completely as a real order would be (`plan` a real `PLANS` value, every per-product field each `Product.mockDetails()` produces) — a seed record with a field left blank/mismatched isn't "no data was entered," it just makes that field look broken wherever it's read back (e.g. an amendment's prefilled form appearing to have blank fields that were actually never seeded in the first place). `QuirioProduct.mockDetails()` (`products.ts`) seeds all eleven of its fields for exactly this reason.

**Dates** are stored as ISO strings (`yyyy-mm-dd`) everywhere in state/mock data (`firstBillingMonth` is the one exception, stored as `yyyy-mm`), converted to `Date` only for computation, and formatted for display with either `formatDDMMYYYY` (`utils.ts`) or `toLocaleDateString("en-IN", ...)` (used in `Approval.tsx`/`Billing.tsx`) — parsing goes through `parseISO`-style manual `split("-")` rather than `new Date(isoString)` to avoid UTC/local timezone shifts.

**Styling** is Tailwind v4 utility classes only (no component library) — colors follow a convention: slate for neutral chrome, indigo for primary/selected nav and dashboard accents, teal for action buttons (Search/Add/Create), emerald/rose/slate for confirmed/rejected/pending status. Icons are inline hand-drawn SVGs (no icon package dependency).

`Modal.tsx` is the shared dialog shell (backdrop click + Escape to close), used by `CreateOrderModal`. `DateRangePicker.tsx` is a shared custom calendar-range popover (no date library dependency, click-once/click-twice with hover-preview highlighting of the in-between range) used by Order List, Approval, and Manager Report filters — Billing's drawer uses `InlineDateRangeCalendar.tsx` instead (see above). `SearchableSelect.tsx` (a searchable single-select combobox) and `AmountRangeSlider.tsx` (a dual-thumb lakh-denominated range slider, styled via the `.dual-range-input` rules in `index.css`) are used across Billing/Approval/Manager Report's Amount and Client/Manager filters. `FilterDrawer.tsx` is the generic right-side filter-drawer shell (currently only used by Billing) — reach for it before building another bespoke filter panel.
